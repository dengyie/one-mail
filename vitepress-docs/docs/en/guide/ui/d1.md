# Initialize/Update D1 Database

## Create Database

Open the Cloudflare console, select `Storage & Databases` -> `D1 SQL Database` -> `Create Database`, and click to create the database.

![d1](/ui_install/d1.png)

After creation, we can see the D1 database in the Cloudflare console.

## Initialize Database

::: warning Note
You can also skip initializing the database and after deployment is complete, go to the admin page's `Quick Setup` -> `Database` section and click the `Initialize Database` button to initialize the database.
:::

Open the `Console` tab, enter the content from the [db/schema.sql](https://github.com/dengyie/one-mail/blob/main/db/schema.sql) file in the repository, and click `Execute` to run it.

![d1](/ui_install/d1-exec.png)

## Update Database Schema

The admin page checks `GET /admin/db_version`; both `need_*` fields are always booleans:

| Database state | `need_initialization` | `need_migration` | Next action |
| --- | --- | --- | --- |
| No application tables | `true` | `false` | Initialize |
| Application tables exist, but the version marker is absent or differs | `false` | `true` | Run schema migration |
| Version matches the code requirement | `false` | `false` | No version migration needed |
| D1 read fails | HTTP error, no status object | Same | Retry the status check |

A missing `db_version` does not mean an empty database. Do not manually stamp the current version: `POST /admin/db_migration` repairs the actual schema and records the version only after every step succeeds. Column-dependent indexes follow column repairs, and replay preserves stored mail. Initialization and migration stop before DDL if the initial status read fails. The status endpoint uses bounded metadata/version reads; it does not replace full schema migration validation.

Migration combines schema reads and batches repairs to leave headroom under the free-plan D1 invocation limit. Batching does not reduce scanned rows or index-write billing. Run schema migration as an occasional admin operation, not as a recurring status check.

Before DDL, primary admin endpoints also check missing email indexes against a maintenance allowance of `70,000 - observed daily rows_written`. A bounded sample budgets every email for every missing index, conservatively overestimating partial indexes. Excess returns **409 `D1_MIGRATION_WRITE_BUDGET`** with `pending_indexes`, `index_write_estimate`, `estimate_capped`, `available_write_rows`, and `quota_confidence`. An estimate reaching the sample limit is not the exact full-table cost. Check authoritative Cloudflare account usage, build the missing indexes in budgeted maintenance windows, then retry migration; do not repeatedly initialize or manually stamp the version. This guard covers email index builds in primary admin initialization/migration only, not every backfill, other tables, shard initialization, CLI, or CI SQL. It is neither an authoritative account balance nor a complete migration budget guarantee.

The page disables actions while an operation is pending and confirms success only after reading the current version. If an operation or its follow-up read fails, **Retry status check** retries only GET; it does not resubmit migration. Leaving the page cancels client requests. A migration already submitted to the server still requires a subsequent status check to confirm its result.

For `schema` updates, please confirm the version you previously deployed.

## Daily quota exhaustion and recovery

When Cloudflare explicitly reports free-tier daily D1 read or write exhaustion, Worker APIs return **503**, with `code` (`D1_DAILY_READ_LIMIT` or `D1_DAILY_WRITE_LIMIT`) and an ISO-8601 UTC `retry_at`. `Retry-After` rounds seconds until the next UTC midnight upwards; the response is not cacheable. Other 5xx errors retain ordinary retry behavior, and partial usage estimates never trip an ingest circuit breaker.

The aggregator stops retries within the failed destination's upload batch and continues healthy destinations. Its existing `SyncState` persists the affected account's deadline across restarts; IDLE, Graph, and polling resume through normal scheduling when due. Folder and status writes also pause the account on explicit exhaustion, and failed batches do not advance watermarks. Transient network errors retain bounded retries. Mutation/outbound queues retain independent 60→120→240→300-second backoff; not every background request is suspended until midnight.

For a deployment during exhaustion, record the authoritative UTC deadline and affected account IDs, stop the aggregator fully, back up its state, persist those account pauses, and start the new version. Do not modify its state from another process while it is running or repeatedly redeem OAuth refresh tokens to test recovery. Deploying cannot replenish exhausted quota: verify a real nonempty ingest after the reset. Read endpoints returning 200 and a RUNNING process do not prove mail synchronization has recovered.
